# Аналитика звонков контакт-центра

Прототип системы автоматического анализа записей телефонных разговоров:
распознавание речи, разделение по говорящим и разбор четырьмя LLM-агентами.

Выполнено в рамках тестового задания на позицию AI Engineer (ЗАО «МТБанк»).

---

## Что делает система

На вход — аудиозапись звонка. На выходе — структурированный разбор:

| Что | Как получается |
|---|---|
| **Транскрипт** | текст реплик с таймкодами и метками «Оператор» / «Клиент» |
| **Классификация** | тема обращения (кредиты / карты / переводы / жалобы / другое) и приоритет |
| **Оценка качества** | чеклист работы оператора и итоговый балл 0–100 |
| **Compliance** | запрещённые формулировки и отсутствующие обязательные пояснения |
| **Резюме** | краткий пересказ разговора и список действий после звонка |

Доступ к анализу — тремя способами: веб-интерфейс, REST API и чат OpenWebUI.

## Архитектура

```
                 аудиофайл или ссылка
                          │
    ┌─────────────────────┼─────────────────────┐
    │                     │                     │
веб-интерфейс        REST API            OpenWebUI Pipeline
web/index.html      POST /analyze      pipelines/mtbank_pipeline.py
    │                     │                     │
    └─────────────────────┼─────────────────────┘
                          │
                 pipeline.py :: analyze()
                          │
        ┌─────────────────┴──────────────────┐
        │                                    │
   ASR-слой                             Multi-agent слой
        │                                    │
  transcriber.py  ─ faster-whisper      classifier.py  ─ тема + приоритет
        +                                quality.py     ─ чеклист оператора
  diarizer.py     ─ pyannote.audio       compliance.py  ─ регулярки + LLM
        ↓                                summarizer.py  ─ резюме + действия
  aligner.py      ─ склейка по времени         │
        ↓                                      │
  roles.py        ─ LLM: кто Оператор,         │
                    кто Клиент                 │
        └─────────────────┬──────────────────┘
                          ↓
              JSON по схеме из задания
```

**Принцип разделения:** каждый слой решает одну задачу и не знает о соседях лишнего.
ASR-слой ничего не знает про агентов, агенты не знают, откуда взялся транскрипт,
а три интерфейса не содержат логики анализа — только приём файла и отображение
результата. Благодаря этому добавление четвёртого интерфейса или замена ASR
не затрагивает остальной код.

### Структура репозитория


## Запуск

### Через Docker (весь стек)

```bash
cp .env.example .env      # заполнить GROQ_API_KEY и HF_TOKEN
docker compose up -d
```

| Сервис | Адрес | Назначение |
|---|---|---|
| Веб-интерфейс и API | http://localhost:8000 | загрузка аудио, `POST /analyze` |
| Документация API | http://localhost:8000/docs | Swagger UI |
| OpenWebUI | http://localhost:3000 | чат-интерфейс |

Первый запуск дольше обычного: скачиваются модели Whisper (~1.5 ГБ) и pyannote.
Они сохраняются в том `model-cache` и при последующих запусках берутся оттуда.

**Подключение пайплайна в OpenWebUI** (разово, после первого запуска):
Admin Panel → Settings → Connections → добавить соединение
URL `http://pipelines:9099`, ключ `0p3n-w3bu!`, тип API — **Chat Completions**
(не «Responses»: сервис pipelines реализует только классический эндпоинт).

### Локально, без Docker

```bash
python -m venv .venv
.venv\Scripts\Activate.ps1          # Windows;  source .venv/bin/activate — Linux/macOS
pip install -r requirements-dev.txt
uvicorn api.main:app --reload
```

Дополнительно нужен установленный **ffmpeg** — им читают аудио faster-whisper и pyannote.

### Обязательные ключи

| Переменная | Где взять |
|---|---|
| `GROQ_API_KEY` | https://console.groq.com — бесплатный тариф |
| `HF_TOKEN` | https://huggingface.co/settings/tokens + принять условия моделей `pyannote/segmentation-3.0`, `pyannote/speaker-diarization-3.1`, `pyannote/speaker-diarization-community-1` |

Остальные параметры (модель LLM, размер Whisper, устройство) необязательны —
значения по умолчанию заданы в `settings.py`, переопределяются через `.env`.

## API

### `POST /analyze`

Принимает **либо** файл, **либо** ссылку на аудио:

```bash
curl -X POST http://localhost:8000/analyze -F "file=@test_data/record1.mp3"
curl -X POST http://localhost:8000/analyze -F "url=https://example.com/call.mp3"
```

Ответ:

```json
{
  "transcript": [
    { "speaker": "Оператор", "start": 0.0, "end": 6.0, "text": "Добрый день, МТБанк..." }
  ],
  "classification": { "topic": "кредиты", "priority": "medium" },
  "quality_score": {
    "total": 100,
    "checklist": {
      "greeting": true,
      "need_detection": true,
      "solution_provided": true,
      "farewell": true
    }
  },
  "compliance": { "passed": true, "issues": [] },
  "summary": "Клиент обратился с вопросом об условиях кредита...",
  "action_items": ["Отправить инструкцию на email клиента"]
}
```

### `GET /health`

Проверка живости сервиса для мониторинга и деплоя.

## Обоснование решений

### Выбор LLM: Groq

Требование задания — любая OpenAI-совместимая модель. Выбран **Groq**
(модель `qwen/qwen3.8-27b`) по трём причинам:

1. **Нет GPU.** Разработка велась на ноутбуке со встроенной графикой. Локальная
   модель конкурировала бы за процессор с Whisper и диаризацией, которые и так
   загружают CPU полностью. Groq выполняет инференс на своей стороне.
2. **Бесплатный тариф** без привязки карты.
3. **OpenAI-совместимый API** — используется официальная библиотека `openai`
   с изменённым `base_url`. Смена провайдера на OpenAI, Together или локальный
   vLLM — это одна строка в `.env`, код менять не нужно.

Замеры: четыре агента последовательно отрабатывают за **1–3 секунды** суммарно,
то есть LLM-часть не является узким местом (см. раздел о производительности).

### Оркестрация агентов: собственный Supervisor

Задание допускало LangGraph или собственный Supervisor-паттерн. Выбран второй.

Агенты **независимы**: все четверо получают один и тот же транскрипт и не
используют результаты друг друга. Для такого сценария граф состояний LangGraph
не даёт ничего, кроме дополнительной зависимости и уровня абстракции — роль
супервизора полностью выполняет функция `analyze()` в `pipeline.py`, которая
вызывает агентов и собирает ответ.

Если бы агенты зависели друг от друга (например, compliance проверял бы только
темы, отмеченные классификатором как рискованные), выбор был бы в пользу
LangGraph.

### Compliance: гибрид регулярок и LLM

Единственный агент, который не полагается на LLM целиком:

- **Детерминированный слой** — точный поиск запрещённых формулировок по списку
  `FORBIDDEN_PHRASES`. Никогда не пропустит буквальное совпадение.
- **LLM-слой** — находит перефразированные нарушения и отсутствие обязательных
  пояснений, которые точным совпадением не поймать.

Результаты объединяются. Проверено на обоих сценариях: на корректном разговоре
оба слоя молчат, на подготовленном «плохом» — регулярка ловит формулировки,
а LLM добавляет объяснение, почему это нарушение.

### Определение ролей говорящих

Диаризация даёт анонимные метки `SPEAKER_00` / `SPEAKER_01` — она различает
голоса, но не знает, кто из них оператор.

Очевидная эвристика «кто заговорил первым, тот и оператор» на реальных данных
**оказалась неверной**: в одной из тестовых записей клиент здоровается первым.
Поэтому роли определяет LLM по содержанию реплик — кто представляется от лица
банка и предлагает помощь, а кто формулирует запрос.

Ответ модели проверяется программно: если в маппинге не оказалось всех меток
из транскрипта, запрос повторяется (механизм `validate` в `call_llm_json`).

### Аудио в чате OpenWebUI передаётся ссылкой

Пайплайн принимает **URL** аудиофайла, а не вложение. Причина: доступ к
прикреплённым в чате файлам со стороны OpenWebUI Pipelines на момент разработки
не имеет стабильного документированного API (открытые обсуждения в репозитории
open-webui). Задание допускает оба варианта: «загрузка через чат **или URL**».
Загрузка файлом при этом полноценно доступна через веб-интерфейс и REST API.

## Тестовые данные и качество распознавания

Пять записей русской речи в трёх форматах, суммарно около 6 минут:

| Файл | Формат | Содержание |
|---|---|---|
| `dialog_full.wav` | WAV, 24 кГц | диалог оператора и клиента, ~2:15, синтез двумя голосами |
| `dialog_full_8k.wav` | WAV, 8 кГц моно | та же запись в телефонном качестве |
| `record1.mp3` | MP3 | живой голос, обращение по кредиту |
| `record2.mp3` | MP3 | живой голос, короткий диалог двух ролей |
| `record3.ogg` | OGG | живой голос, вопрос по вкладам |

Диалог синтезирован скриптом `scripts/generate_test_data.py` по сценарию из
`docs/sample-dialog.md` двумя разными голосами (edge-tts). Благодаря этому
эталонный транскрипт **точно** соответствует записи — WER считается относительно
исходного текста, а не расшифровки на слух. Записи живым голосом расшифрованы
вручную.

### WER

Расчёт: `python -m scripts.compute_wer` (библиотека `jiwer`).

| Файл | WER |
|---|---|
| dialog_full.wav | 9.36% |
| dialog_full_8k.wav | 9.85% |
| record1.mp3 | 0.00% |
| record2.mp3 | 0.00% |
| record3.ogg | 0.00% |

Перед сравнением оба текста нормализуются: приводятся к нижнему регистру, из
них убирается пунктуация. Без нормализации WER на том же файле составлял 22.93%
вместо 9.36% — то есть больше половины «ошибок» приходилось на расхождения в
знаках препинания, а не на неверно распознанные слова.

Телефонное качество (8 кГц) ожидаемо даёт результат чуть хуже исходной записи:
9.85% против 9.36%.

## Производительность

Замеры на CPU (Intel Core i5-13420H, без GPU), запись 2 минуты 15 секунд:

| Этап | Время |
|---|---|
| Распознавание речи (Whisper medium) | ~95 c |
| Диаризация (pyannote) | ~127 c |
| Определение ролей | ~1.5 c |
| Четыре агента | ~1.3 c |

Основное время — ASR и диаризация на процессоре; LLM-часть занимает секунды.
Модели загружаются в память один раз при старте сервиса (ленивая инициализация
в `transcriber.py` и `diarizer.py`), поэтому первый запрос заметно дольше
последующих: короткая запись после прогрева обрабатывается за **13–18 секунд**.

Ускорение при наличии GPU — без изменений кода, через `.env`:

```
WHISPER_DEVICE=cuda
WHISPER_COMPUTE_TYPE=float16
```

## Логирование

Логи пишутся в stdout в формате JSON — по одному событию на строку, чтобы их
можно было собирать и фильтровать машинно (Loki, ELK и подобные):

```json
{"timestamp": "2026-09-07 15:54:30", "level": "INFO", "event": "agent_call",
 "agent": "classifier", "input_segments": 28, "input_preview": "Добрый день, МТ Банк...",
 "output": {"topic": "кредиты", "priority": "low"}, "duration_sec": 0.27}
```

Логируется вход и выход каждого агента и время его работы. Транскрипт в поле
`input_preview` обрезается — иначе каждая запись содержала бы полный текст
разговора четыре раза подряд.

## Известные ограничения

- **Скорость на CPU.** Запись в 5 минут обрабатывается несколько минут.
  Для продакшена нужен GPU либо вынос ASR в облачный сервис.
- **Требования к памяти.** Whisper medium и pyannote вместе занимают несколько
  гигабайт. На машине с 16 ГБ ОЗУ не стоит одновременно держать поднятый
  Docker-стек и запускать тесты локально — второй экземпляр моделей
  не поместится в память (`mkl_malloc: failed to allocate memory`).
  Перед локальным прогоном тестов остановите контейнеры: `docker compose stop`.
- **Галлюцинации на коротких записях.** На записи из одной реплики без ответа
  оператора суммаризатор однажды описал действия оператора, которых в
  транскрипте не было. На полноценных двусторонних разговорах не воспроизводится.
- **Точность диаризации** не измерялась численно (DER) — проверялась
  сопоставлением с транскриптом вручную.
- **Список запрещённых фраз** составлен как демонстрационный; в реальном
  внедрении его формирует комплаенс-подразделение банка.
